### What the benchmark does and does not show
- One run per concurrency level, short prompts (~40 tokens), 256 output tokens, temperature 0. No variance estimate.
- Per-request speed barely drops from 1 to 64 concurrent (22.4 → 19.7 tok/s), so batching is nearly free:
  **always send requests concurrently**; sequential calls waste ~98% of capacity.
- Single-stream 22.4 tok/s is low. HYPOTHESIS (not verified): BF16 decode is GPU-memory-bandwidth bound
  (15 GB of weights read per token). A 4-bit model would test this.
- RAG prompts (thousands of tokens) will be slower and the 37,920-token KV cache caps how many fit at once
  (e.g. ~9 concurrent 4k-token requests). Must be measured with realistic prompts in Phase 3/4.
- A BF16 7B generator leaves ~1.5 GB VRAM: **no room for a second model on the GPU**. Generator + verifier
  together needs 4-bit models or sequential stages (to be measured, not assumed).

## How to serve a model (current working recipe)
    bash scripts/serve_vllm_docker.sh [MODEL] [REVISION] [extra vllm args]   # prints VLLM_READY
    bash scripts/run_phase0_bench.sh                                          # optional sanity benchmark
    docker rm -f vllm                                                         # stop, frees the GPU
Models are downloaded into the WSL HF cache with `bash scripts/download_model.sh MODEL REVISION`
(plain HTTPS; Xet transfer failed on this network) and mounted into the container read-write.
